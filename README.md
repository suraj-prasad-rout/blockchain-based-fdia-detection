# FDIA Mitigation in Smart Microgrids Using Blockchain



## Overview



This project investigates the detection of False Data Injection Attacks (FDIAs) in a simulated smart microgrid and evaluates blockchain-based measurement integrity verification.



The system combines power-system simulation, DC state estimation, residual-based anomaly detection, and a Solidity smart contract that stores cryptographic fingerprints of measurement payloads.



The objective is to evaluate what residual-based detection and blockchain integrity verification can each establish, and to identify their limitations.



## Objectives



- Simulate a small electrical microgrid using pandapower.

- Generate synthetic measurements and reference states.

- Estimate the microgrid state using Weighted Least Squares (WLS).

- Simulate random, targeted, and model-consistent FDIA scenarios.

- Detect measurement anomalies using a residual-based detector.

- Register measurement payload hashes in a Solidity smart contract.

- Verify whether a measurement payload matches its previously registered hash.

- Evaluate detection metrics, estimation error, transaction latency, verification latency, and gas consumption.



## System Architecture



1\. \*\*Microgrid simulation:\*\* Creates the electrical network and generates measurements.

2\. \*\*State estimation:\*\* Estimates bus voltage angles using a DC measurement model and WLS.

3\. \*\*Attack simulation:\*\* Generates clean and manipulated measurement scenarios.

4\. \*\*Residual detector:\*\* Compares the residual statistic with a detection threshold.

5\. \*\*Blockchain registry:\*\* Records payload hashes and supports later integrity verification.

6\. \*\*Evaluation:\*\* Calculates performance metrics and generates CSV reports and plots.

## Setup



### 1. Create and activate a Python virtual environment



On Windows PowerShell:



```powershell

python -m venv .venv

.\\.venv\\Scripts\\Activate.ps1

```



### 2. Install Python dependencies



```powershell

python -m pip install --upgrade pip

python -m pip install -r requirements.txt

```



### 3. Install JavaScript dependencies



From the project root:



```powershell

npm ci

```



### 4. Compile the smart contracts



```powershell

npx hardhat compile

```



### 5. Start the local blockchain



Open a separate PowerShell terminal in the project root and run:



```powershell

npx hardhat node

```



Keep this terminal running while executing blockchain experiments.



### 6. Deploy the measurement registry



With the Python virtual environment activated in the other terminal:



```powershell

python -m src.blockchain.compile\_deploy

```



Use the ABI and contract address generated by the deployment script. A restarted local Hardhat node has a fresh chain state, so deploy the contract again after restarting it.



## Running the Experiments



Run the commands from the project root with the Python virtual environment activated.



### Generate or inspect the baseline



```powershell

python -m src.evaluation.run\_baseline

```



### Run WLS state estimation



```powershell

python -m src.evaluation.run\_wls

```



### Run Phase 2 FDIA experiments



```powershell

python -m src.evaluation.run\_experiments

```



### Register and verify measurement payloads



With the local blockchain running and the registry deployed:



```powershell

python -m src.blockchain.register\_batch

python -m src.blockchain.verify\_batch

python -m src.blockchain.security\_checks

```



### Run blockchain benchmarks



```powershell

python -m src.evaluation.run\_blockchain\_benchmark

python -m src.evaluation.run\_blockchain\_fdia\_experiment

```



### Run the integrated experiment



```powershell

python -m src.evaluation.run\_integrated\_experiment

```



The integrated experiment uses 100 seeds and evaluates clean, random-attack, targeted-attack, and model-consistent-attack scenarios. It interacts with the local blockchain, so the Hardhat node and a deployed registry must be available.



\*\*Important:\*\* The integrated experiment uses fixed batch-ID prefixes. Do not rerun it against the same deployed chain without changing those prefixes or resetting and redeploying the local chain. The smart contract rejects duplicate batch/index registrations.

## Experimental Results



### Residual-based detection



In the 100-seed integrated experiment, the residual detector produced the following overall metrics:



| Metric              | Result |

| ------------------- | -----: |

| True positives      |     97 |

| True negatives      |     97 |

| False positives     |      3 |

| False negatives     |    203 |

| Precision           | 97.00% |

| Recall              | 32.33% |

| F1-score            | 48.50% |

| False-positive rate |  3.00% |



The detector identified 91% of random attacks but only 3% of targeted attacks and 3% of model-consistent attacks in the evaluated scenarios.



### Blockchain verification



In the integrated experiment, changed payloads failed verification against the clean payloads previously registered as references. When an attacked payload was registered first, that payload verified against its own registered hash.



This demonstrates integrity verification against a stored reference, not independent validation of the physical truth of the measurement.



### Local blockchain performance



Measured on the local Hardhat development chain:



| Operation    | Median latency | P95 latency |

| ------------ | -------------: | ----------: |

| Submission   |      20.534 ms |   28.598 ms |

| Verification |       7.110 ms |   10.226 ms |



These figures describe the local experimental setup and should not be treated as production-network performance estimates.

## Limitations



1\. \*\*Blockchain does not prove physical truth.\*\* A cryptographic hash proves that a payload matches a registered fingerprint; it does not prove that the measurement was accurate when recorded.

2\. \*\*Compromised authorized sensors remain a risk.\*\* A malicious or compromised authorized source can submit false measurements that are then immutably recorded.

3\. \*\*Residual detection has limitations.\*\* Model-consistent or carefully targeted attacks may evade the implemented residual detector.

4\. \*\*Synthetic test environment.\*\* The reported detection results are based on the implemented simulated network and attack scenarios, not a field deployment.

5\. \*\*Local blockchain environment.\*\* Hardhat is a local development chain, not a production consortium blockchain with deployed validator nodes and a production consensus configuration.

6\. \*\*Performance depends on the environment.\*\* Latency and gas results from this prototype should not be generalized to other networks without further experiments.



## Conclusion



The project demonstrates a prototype that combines WLS-based state estimation, residual-based FDIA detection, and blockchain-backed measurement integrity verification.



The experiments show that residual detection and blockchain verification address different problems. Residual analysis can identify certain measurement anomalies, while blockchain can reveal changes relative to a previously registered payload. Combining the two provides complementary checks, but neither alone guarantees that every measurement is physically valid.



Future work can investigate redundant sensor measurements, physical plausibility checks, stronger detection of stealthy attacks, and evaluation on a multi-node permissioned blockchain.



## Reproducibility and Security



- Run blockchain experiments only against the intended development network unless a separately reviewed deployment configuration is used.

- Never commit private keys, RPC credentials, or populated `.env` files.

- Preserve experiment configurations and generated result files when preparing the research submission.

- Record the Python, Node.js, Hardhat, and Solidity versions used for each final experiment.
